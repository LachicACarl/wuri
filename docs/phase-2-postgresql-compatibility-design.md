## Compatibility matrix

| Finding | Existing implementation | PostgreSQL change required | Risk | Verification method after clearance |
|---|---|---|---|---|
| Connection and rows | `sqlite3.connect`, `sqlite3.Row`, one connection per `connection()` context; app code accesses rows by string key. | Add a PostgreSQL driver and use mapping rows (for example, psycopg `dict_row`) or an equivalent explicit result adapter. Keep connection lifecycle centralized in `Database`. | Medium: result/NULL/type behavior changes can alter API serialization. | Exercise each database method against a temporary PostgreSQL database and compare result shapes to documented contracts. |
| Bind parameters | Hundreds of queries use SQLite `?` placeholders. | Rewrite and review each query for the selected driver's placeholder style. Use bound parameters; do not do textual global replacement. | High: placeholder order, quoting, and SQL behavior can be corrupted by mechanical replacement. | Query-level CRUD, boundary, and adversarial-value cases; static review of every changed statement. |
| SQLite connection setup | `PRAGMA foreign_keys = ON`; migration runner uses `PRAGMA foreign_key_check`. | PostgreSQL enforces declared foreign keys without per-connection PRAGMA. Replace the migration-time check with explicit constraint validation/catalog checks. | Medium: existing invalid references could prevent constraint creation or reveal prior integrity issues. | Count and inspect orphan references in a disposable copy before constraints are accepted. |
| Migration execution | Python creates `schema_migrations`; sorted SQL scripts are run with `executescript`, then migration names are recorded. | Create a separate PostgreSQL migration set and migration runner; record ordered version, checksum, applied time, and transaction outcome. Never run SQLite scripts against PostgreSQL. | High: partial application and incorrect version tracking can leave incompatible schemas. | Apply all PostgreSQL migrations to a fresh disposable DB, test restart/idempotency policy, and inject migration failure. |
| Migration 004 | Disables SQLite FK checks, begins immediate transaction, rebuilds examples, uses `INSERT OR IGNORE`, drop/rename, then checks FK integrity. | Write a PostgreSQL-specific transactional migration. Explicitly preserve the source-row selection, duplicate/conflict behavior, table constraints, and child foreign keys. | High: data loss or changed referential behavior during table replacement. | Synthetic fixture reconciliation before/after, FK checks, counts, unique collision cases, and rollback of a failed migration. |
| Migration 005 SQL/functions | Generates audit IDs with `lower(hex(randomblob(16)))`, JSON via `json_object`, alters data and invalidates legacy dataset approvals. | Generate IDs through the application’s existing UUID helper or a documented PostgreSQL UUID expression; replace JSON expression with PostgreSQL JSON construction or parameterized `json.dumps`. Preserve the approval invalidation and audit event as one transaction. | High: audit/provenance meaning could be lost or invalidated records could remain approved. | Compare exact affected record IDs/statuses and audit payloads on synthetic data; verify transaction rollback. |
| Application SQL functions | `json_extract(configuration_json, '$.evaluation_scope')` at `database.py:710,720`; timestamps use `CURRENT_TIMESTAMP`; `ON CONFLICT ... DO UPDATE` at `database.py:1417`. | Use PostgreSQL JSON operators after choosing text vs JSONB; review timestamp type/default/time-zone semantics; translate and verify upsert targets/update clauses. | Medium-high: JSON parsing, timestamp formats/order, and upsert conflict semantics may differ. | Test each supported JSON shape, timestamp round trip/order, and both insert and conflict-update branches. |
| ID generation | Most IDs use string prefixes plus Python `uuid.uuid4()` in `database.py:1967`; one audit path and migration 005 use SQLite randomblob. | Preserve existing TEXT IDs and Python UUID generation for minimal data compatibility; remove SQLite-only randomblob. Do not convert to UUID columns without proving all IDs meet that format and updating every FK/API contract. | Medium: mixed ID formats and foreign-key mismatch. | Check all generated ID classes and FK joins using synthetic fixtures. |
| Types and constraints | IDs/JSON/times are mostly `TEXT`; file sizes and indexes are `INTEGER`; scores use `REAL`; schema has PK/FK/UNIQUE/CHECK and indexes. | Start with compatible text IDs; map integer to PostgreSQL integer/bigint based on ranges, real to double precision or a chosen exact numeric type, and recreate all constraints/indexes. Select JSON and time types only with application conversion changes. | High: silent truncation, precision changes, constraint behavior, or API serialization changes. | Compare schema catalog, boundary values, checks, indexes, and serialized responses. |
| JSON values | App writes `json.dumps` strings and reads with `json.loads`; migrations store JSON fields as `TEXT`. | Initial migration can retain text JSON to preserve the current application contract; longer-term JSONB requires explicit driver adapters and removal/rewriting of manual JSON serialization. | Medium: double encoding or changed null/number/string behavior. | Round-trip representative nested values including nulls, lists, booleans, Unicode, and decimals. |
| Time values | `CURRENT_TIMESTAMP` writes textual timestamps; app also supplies some timestamps. | Decide UTC/time-zone policy; normalize to `TIMESTAMPTZ` at a defined boundary or initially preserve text values with explicit formatting. Do not mix implicit conversion and string comparisons. | Medium-high: ordering, expiry, and audit chronology changes. | Test migrations and comparisons around timezone offsets, precision, and expiry boundaries. |
| Errors | `main.py` catches `sqlite3.IntegrityError` and `sqlite3.Error` at multiple endpoints. | Map PostgreSQL unique, FK, check, and operational exceptions into existing API/domain error behavior; avoid leaking driver details. | Medium: changed 409/422/500 responses or leaked SQL errors. | Test each constraint violation and connection failure for expected sanitized response. |
| Transaction boundaries | `connection()` commits when its context exits and rolls back on exception. Methods may group several statements in one context; imports also coordinate object and DB operations. | Preserve atomic groups, specify isolation level, and avoid implicit commits. Use a bounded connection pool appropriate to Render process/workers. | High: partial records, race conditions, or connection exhaustion. | Concurrency, rollback, deadlock/serialization, and pool exhaustion tests. |
| Data access/authorization | Custom auth and application queries scope records through user/institution memberships. | Keep those checks. If adding PostgreSQL RLS, design trusted per-request identity context and a non-owner, non-BYPASSRLS app role; RLS is not automatically applied to the custom session identity. | High: cross-institution disclosure or mistaken assumption that a service role is constrained by RLS. | Negative tenant-isolation tests with two institutions and multiple roles. |

## Recommended access strategy

Use the existing `Database` class as the boundary, but perform a controlled query rewrite to a PostgreSQL driver with mapping rows and explicit transaction management. Keep SQL in the existing data-access layer unless the migration work proves a specific query is better expressed through an abstraction. This avoids a wholesale ORM/domain rewrite while still requiring every SQL statement and migration to be reviewed. A token-rewriting compatibility shim is not recommended: SQL placeholders, row behavior, SQLite functions, migration SQL, and exception types all differ, and a shim cannot safely infer semantics.

An SQLAlchemy Core conversion is a viable alternative if maintainability and future portability justify a larger refactor. It would replace much of the current handwritten SQL and parameter/result handling, so it should be separately estimated and tested rather than introduced mechanically during deployment preparation. No option has been implemented or benchmarked.

## Security and unresolved choices

- Keep the current custom login/session system initially unless a separate identity migration is approved. Supabase Auth would be a product/authentication redesign, not a database migration.
- Never put a database connection string or service-role/secret API key in React or any `VITE_*` variable.
- The Supabase service-role key exposed in the prior conversation has **UNCONFIRMED** rotation status. Do not use it; an authorized owner must deactivate it and confirm that it is no longer valid.
- The value pasted in the prior conversation was identified as a service-role credential. Treat it as privileged and compromised until an authorized owner confirms deactivation. Do not use it in browser code or assume RLS constrains privileged service-role access.
- If FastAPI uses direct PostgreSQL access, use a dedicated least-privilege DB role rather than the project owner. Application authorization remains required. RLS can be added as defense in depth only after a trustworthy tenant-identity context is designed.
- Keep separate development and production projects and do not move institutional/research data until its use is authorized.

No PostgreSQL code or migration has been written. This design is not evidence of compatibility or deployment readiness.

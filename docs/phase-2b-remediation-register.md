## Executive summary

This register turns the Phase 2A findings into dependency-ordered decisions and acceptance gates for possible future PostgreSQL/Supabase and Render work. It does not authorize implementation, provider access, data transfer, testing, or deployment. The current security decision remains NO-GO. The suspicious cached revision and October 22 forced-update provenance remain unresolved, and the previously exposed Supabase service-role credential’s revocation/rotation remains unconfirmed.

The first permissible work is documentation correction and obtaining authorized decisions. Database migration implementation must wait for written security clearance and closure of the design decisions that affect transaction semantics, schema conversion, authorization, and object recovery. The first future Supabase integration test must use a separate isolated development project, least-privilege credentials, and synthetic data, after explicit written authorization for runtime/provider access. A passing design review is not runtime evidence.

This register is based on the local Phase 2A report, four Phase 2 design documents, Phase 1F handoff, and static source references listed below. Provider settings, current Supabase key status, database contents, repository-host audit records, and institutional approvals were not independently verified.

## Required approvals

- **Repository maintainer/security owner:** forced-update authorization/provenance and the exact reviewed code; whether and how controlled runtime checks may resume.
- **Independent security reviewer:** complete static behavior/provenance assessment of suspicious generated code and any conditions on use of the clean local tree.
- **Supabase project owner:** Dashboard revocation/rotation of the exposed privileged key, private confirmation of revocation, and approved least-privilege development credential/project setup.
- **Database/application owner:** PostgreSQL driver, transaction/locking semantics, migration plan, role grants, connection/pool policy, and rollback decision owner.
- **Institutional data custodian/privacy owner:** whether institutional records/documents may be copied, purpose, access, retention, deletion, and recovery obligations.
- **Research owner/researcher:** approval-state behavior, research import retention, authorized synthetic/real research data, and any separate protocol approval. This does not authorize A0–A4 or readiness scoring by itself.
- **Deployment owner:** Render service/runtime/domain/secrets/network/health/persistence configuration and operational monitoring/recovery ownership.
- **Test operator/security approver:** written authorization for the exact first provider/runtime test, data constraints, stop conditions, and evidence retention.

No approval is inferred from a prior design document, account creation, repository access, or a successful documentation review.

## First Supabase integration test prerequisites

The first future Supabase test is a narrowly scoped **synthetic-data development integration test**. It is not authorized now. All prerequisites must be met before any connection is attempted:

1. SEC-01 is closed with written authorization that explicitly covers runtime/provider connectivity and names allowed operations.
2. SEC-02 is privately confirmed by the authorized owner: the exposed service-role key is revoked, and any new development credential is created/stored through approved channels. Do not share or commit either value.
3. A separate isolated development Supabase project/database is approved; it contains no institutional, personal, or research production data and cannot be mistaken for production.
4. A least-privilege server-side database role and authentication/RLS decision are implemented and reviewed. No service-role key is used as the normal app role; no credential is sent to React or a `VITE_*` variable.
5. Phase 2 design gaps relevant to this test are closed: SQL inventory, migrations, transaction/concurrency behavior, exception mapping, schema conversion, auth/membership policy, and startup lifecycle.
6. Test plan states exact schema/data fixtures, assertions, expected failures, resource limits, stop conditions, cleanup, and evidence logging. Fixtures are synthetic and contain no real names, documents, secrets, or institution records.
7. An isolated application configuration and deployment/network route are reviewed. CORS/cookies are irrelevant to a database-only test unless API/browser traffic is included; if included, those settings must also be approved and tested separately.
8. Rollback plan for the test environment is approved; it must not target, mutate, or use the local SQLite source database.

Passing this test can establish only the properties it directly exercises in that development configuration. It does not prove production security, provider availability, object storage correctness, deployment readiness, or permission to use real data.

## Rollback requirements

- Preserve the original SQLite file, existing user changes, snapshots, security evidence, and a separately verified backup; never overwrite the source as part of migration.
- Identify every writer and define a controlled write-freeze window before final export. Record who owns the freeze and the authority switch.
- Define export order from the complete FK graph, explicit conversion rules, migration version/checksum state, resumable import behavior, and approved reconciliation thresholds.
- Reconcile row counts and key relationships, constraint/conflict outcomes, null/status distributions, JSON, timestamps, approvals/audit provenance, and every object key/checksum/size before cutover.
- Declare the exact point at which PostgreSQL becomes authoritative. Before that point, return to unchanged SQLite only if no authoritative PostgreSQL writes occurred. After it, do not switch blindly: use the approved forward-fix or separately designed and tested reverse-data procedure.
- Treat database and object storage as separate recovery systems. Specify compatible restore points, object versioning/deletion recovery, keys/policies, RPO/RTO, and restore operator.
- Rehearse restore/rollback only in an isolated environment after written authorization; a plan or successful schema migration is not a rollback rehearsal.

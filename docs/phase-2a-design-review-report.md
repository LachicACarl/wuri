# Phase 2A — Design Review and Migration Readiness Audit

**Review date:** 2026-10-23  
**Review mode:** Static inspection of the current local worktree only  
**Implementation decision:** **NO-GO**

## Executive summary

The four Phase 2 documents consistently describe planning rather than completed PostgreSQL, object-storage, or Render work. They correctly keep the runtime/security hold at NO-GO, mark Supabase credential rotation unconfirmed, and avoid claiming deployment or migration readiness. Their cautions against replaying SQLite migrations, using the exposed service-role credential, relying on ephemeral service storage, or treating a database rollback as sufficient after PostgreSQL writes are sound.

The designs are not yet implementation-ready. The PostgreSQL compatibility inventory misses application-level SQLite transaction statements (`BEGIN IMMEDIATE`) and a route-level SQLite random-ID expression, and it does not connect changed database exception classes to concrete upload compensation paths. The storage design describes a useful recovery pattern but leaves the operation state machine, idempotency rules, and database/object ordering to be specified. The rollback plan correctly states its key data-loss boundary but needs an operational cutover/freeze and recovery procedure. The RLS boundary, role model, and trusted tenant context remain design questions. The Render document is appropriately cautious, but its health-check, process-start, deployment persistence, and provider settings are not verified.

No migration or deployment code should be written from these plans until the corrections and unresolved decisions listed below are addressed, and the applicable security and credential gates are resolved. This review did not contact a maintainer or verify provider account state.

## Findings

### High

1. **The compatibility inventory omits application-level SQLite transaction behavior and one route-level SQLite SQL expression.** The compatibility design covers SQLite connection handling and migration 004 (`phase-2-postgresql-compatibility-design.md:39-45,51`), but application code also executes `BEGIN IMMEDIATE` in multiple multi-step research operations (`backend/app/database.py:1101-1103,1393-1395,1447-1449,1478-1480,1665-1667,1728-1730`). PostgreSQL has no direct equivalent with identical locking semantics; isolation, locking, and concurrent authorization/update behavior need explicit redesign. Separately, document download inserts an audit row using `lower(hex(randomblob(16)))` (`backend/app/main.py:590-596`), while the design only discusses the matching migration-005 expression and does not call out this route occurrence (`phase-2-postgresql-compatibility-design.md:44-46`). **Required correction:** inventory every raw SQL statement in both `database.py` and route handlers, classify each transaction/SQLite function, and specify the PostgreSQL semantics and concurrency expectations before implementation.

2. **Database exception remapping is not tied to cleanup and API behavior.** The design notes that `sqlite3` exceptions must map to PostgreSQL/domain errors (`phase-2-postgresql-compatibility-design.md:50`), but current routes catch SQLite-specific exceptions and use different cleanup behavior. For example, document persistence catches only `(PermissionError, OSError, ValueError)` and deletes the saved object in that branch (`backend/app/main.py:531-539`); research import catches `sqlite3.Error` (`backend/app/main.py:928-936`). After a driver change, failures may bypass cleanup or surface as unhandled errors. **Required correction:** specify a driver-independent domain exception layer and enumerate endpoint status/error mapping, transaction rollback, object compensation, and sanitized logging for constraint, operational, and connection failures.

3. **Storage and database changes require a defined recoverable operation protocol.** The storage design appropriately rejects assuming a cross-system transaction and proposes pending state, retries, tombstones, and reconciliation (`phase-2-private-document-storage-design.md:24-26`), but does not define durable state transitions, unique/idempotency keys, which system is authoritative at each transition, safe retry after process termination, or who runs reconciliation. Existing behavior confirms why this matters: local upload saves the file before metadata persistence (`backend/app/main.py:531-539`; `backend/app/storage.py:12-16`), while deletion removes the database record before deleting the file (`backend/app/main.py:654-661`). **Required correction:** include upload/delete state diagrams or transition tables, idempotency and retry rules, failure ownership, and reconciliation outcomes before choosing an adapter or schema.

4. **Security authorization does not yet define a deployable PostgreSQL/RLS identity boundary.** The compatibility design correctly warns that WURI’s custom session identity is not automatically a PostgreSQL RLS identity and says the app role must be non-owner/non-BYPASSRLS (`phase-2-postgresql-compatibility-design.md:52,60-67`); the storage design likewise notes the custom HMAC cookie is not a Supabase Auth JWT (`phase-2-private-document-storage-design.md:30-34`). The actual API performs membership checks in FastAPI (`backend/app/main.py:386-407`). The design still leaves unresolved whether access is exclusively backend-mediated or RLS is also used, how a trusted per-request tenant context reaches PostgreSQL, how it is cleared on pooled connection reuse, and which role/privileges are required. **Required correction:** settle this boundary and document role grants, tenant-context lifecycle, bypass protections, and negative isolation cases before implementing database access. Do not assume RLS protects requests made with a privileged service-role credential.

### Medium

5. **Rollback is honest about the post-cutover data-loss boundary but lacks a complete cutover/runbook.** The migration plan says to keep SQLite unchanged and acknowledges that switching back after PostgreSQL authoritative writes loses them absent reverse export (`phase-2-database-migration-and-rollback.md:24-30`). It also proposes a write freeze and final copy (`:16,22`), but does not specify how to identify/freeze all writers, the acceptance/abort decision point, how long the freeze lasts, how a failed or interrupted export/import resumes, who owns the authoritative-write switch, or the exact rollback cutoff. **Required correction:** define these operational decisions, including forward-recovery versus reverse-export criteria, restore points for both database and objects, and how writes are handled during rollback. Preserve the existing source database and backup unchanged.

6. **Migration ordering and SQLite-specific migration semantics need a complete reviewed mapping.** The docs correctly warn that the parent-first list is abbreviated and must be derived from the full FK graph, and identify migration 004 conflict semantics and migration 005 approval invalidation (`phase-2-database-migration-and-rollback.md:34-41`; compatibility design `:27-31,43-44`). They do not yet provide a per-migration PostgreSQL transformation, data preconditions, or explicit row-level acceptance rules for `INSERT OR IGNORE`. The rollback plan also says migration 006–008 add “evidence authorization, review, and malware scan state defaults” (`phase-2-database-migration-and-rollback.md:40`), a compressed description that should be checked against each actual migration’s exact tables/columns rather than treated as a complete migration map. **Required correction:** produce a reviewed migration-by-migration inventory, FK dependency graph, conflict policy, data effects, and acceptance/reconciliation criteria.

7. **JSON, timestamp, numeric, and constraint policies remain alternatives rather than decisions.** Both database documents identify TEXT/JSON, timestamp, numeric precision, and constraint differences (`phase-2-postgresql-compatibility-design.md:47-51`; migration plan `:43-51`), but defer choices. This is appropriate for a design stage, but implementation cannot proceed until API serialization, null handling, UTC/timezone/precision, decimal/score behavior, text comparisons, and delete/cascade semantics are specified and validated against representative synthetic fixtures. **Required correction:** record a single initial compatibility policy for each persisted field family and a conversion/reconciliation rule.

8. **Render startup and health behavior are explicitly unverified and need implementation decisions.** The Render plan correctly states that there is no production start command or HTTP readiness endpoint and that root `/` does not test dependencies (`phase-2-render-deployment-plan.md:8-11,22,50-52`). Source confirms the root route returns only a static status (`backend/app/main.py:216-218`) and the command-line readiness check writes a storage probe and opens SQLite (`backend/app/deployment_readiness.py:17-50`); importing `main.py` constructs `Database()` and `PrivateStorage()` at module scope (`backend/app/main.py:47-49`), and `Database` creates its parent directory and initializes/migrates SQLite (`backend/app/database.py:14-19,35-61`). **Required correction:** define side-effect-safe startup/lifespan behavior, a production process command, and distinct liveness/readiness semantics against the selected database/storage dependencies. Do not use the CLI preflight as an HTTP health check or run it under the current NO-GO.

9. **Deployment configuration is a plan, not evidence of provider readiness.** The proposed Vite `dist` output, static route fallback, Render service configuration, network reachability, pool mode, filesystem durability, production domain, CORS origins, and cookie behavior are labeled expected/unresolved (`phase-2-render-deployment-plan.md:7,20,22,35-46,50-59`). Source confirms current CORS only allows local origins and methods GET/POST (`backend/app/main.py:33-45`), while the API includes PUT, PATCH, and DELETE routes (for example `backend/app/main.py:251,292,630,649`). The plan flags this mismatch. **Required correction:** retain these as open decisions until the actual provider plan, deployment origins, database connection mode, and HTTPS/cookie/CSRF design are documented; do not label the service deployable before authorized verification.

10. **Research import object lifecycle is not fully addressed.** The storage design identifies that research import files are stored locally and says no download/delete route was found in the inspected inventory (`phase-2-private-document-storage-design.md:12`), then recommends retention classes (`:26`). It leaves unresolved whether these objects are retained as audit/provenance artifacts, how a dataset/import deletion affects them, and which data/research owner approves disposal. **Required correction:** define access, retention, deletion, backup, and migration behavior for import artifacts separately from institutional evidence.

11. **Schema requirements for object metadata and malware provenance need a target mapping.** The storage design recommends storing content type, object key, checksum, size, scan status/time/tool, and provenance (`phase-2-private-document-storage-design.md:22`). The source inventory in the PostgreSQL design notes current metadata and the malware scan migration (`phase-2-postgresql-compatibility-design.md:30-31`), but neither document maps every proposed field to an existing column or identifies which require a schema change. **Required correction:** add a field mapping covering original/sanitized filename, detected content type, size, checksum, storage key, scan result/time/tool, provenance/permission, and object lifecycle state; identify migration and API changes for new fields.

12. **Security and external-state prerequisites remain unresolved.** The plans consistently state that the security hold is NO-GO and Supabase key rotation is unconfirmed (`phase-2-postgresql-compatibility-design.md:3,64-67`; migration plan `:15`; Render plan `:65-72`). Phase 1F records the unanswered forced-update provenance and reviewer questions (`phase-1f-security-hold-maintainer-handoff.md:43-60,66-75`). These are not verified clearances or provider facts. **Required correction:** obtain and retain the authorized written security decision before any runtime, migration, or deployment work; obtain private confirmation that the exposed privileged key is deactivated before any connection attempt; separately resolve data-owner/research approvals before moving real records or documents.

### Low

13. **The credential warning is duplicated.** The PostgreSQL design repeats the service-role exposure and unconfirmed-rotation warning in adjacent bullets (`phase-2-postgresql-compatibility-design.md:64-65`). This is editorial only; consolidate when revising that design, without removing the precaution.

### Informational

14. **The documents do not claim completed tests, migration, or deployment.** Their status language is consistent with source and the Phase 1 baseline: PostgreSQL driver/adapter and migration implementation are absent by their inspected inventories; the storage implementation is local filesystem (`backend/app/storage.py:7-16`); the Render plan is explicitly proposed and unverified (`phase-2-render-deployment-plan.md:3,76-78`). This report independently confirms only static source/document observations, not environment/provider state.

## Missing requirements and unresolved evidence

- Exact full query inventory and transaction map across `database.py` and `main.py`, including every `BEGIN IMMEDIATE`, SQLite function, placeholder, upsert, and route exception handler.
- PostgreSQL driver/row representation, connection/pool lifecycle, transaction isolation/locking policy, retry policy, and sanitized domain-error contract.
- PostgreSQL migration design for each of the eight existing SQLite migrations; conflict semantics; FK graph; checksum/failure/concurrent-run behavior; schema and data acceptance rules.
- Explicit data conversion choices for IDs, JSON, timestamps, numeric values, constraints, defaults, and API serialization.
- Authoritative database/object operation state machines with idempotency, retry, cleanup, reconciliation, and audit rules.
- Target mapping for document and research-import object metadata, access, retention, and deletion.
- Trusted custom-session-to-database tenant identity design and, if RLS is selected, exact least-privilege role grants and pooled context lifecycle.
- Cutover write-freeze procedure, operator and decision owner, reconciliation gate, rollback cutoff, backup/restore evidence, and post-cutover write treatment.
- Actual provider configuration and external evidence: authorized security decision, key deactivation, data/research approvals, domains/origins, service filesystem policy, database endpoint/pooler requirements, and production secret configuration. None was checked or confirmed in this review.

## Required corrections before implementation

1. Expand the PostgreSQL compatibility inventory to cover all application SQL and transaction statements, including the route-level random-ID expression and every SQLite exception handler.
2. Specify the driver-independent error/transaction boundary and how each upload/import/delete path compensates or reaches a durable recoverable state on each failure.
3. Add explicit upload and deletion state machines, idempotency keys, retries, reconciliation ownership, and audit/retention behavior across database and object storage.
4. Complete the migration-by-migration SQL/data-effects map, FK ordering, conflict rules, and acceptance checks; choose conversion policies for JSON, time, numbers, IDs, and constraints.
5. Resolve backend-only authorization versus RLS and document least-privilege credentials, trusted tenant context, pool reset, and isolation assumptions.
6. Complete a cutover/rollback runbook with freeze duration/ownership, final copy/reconciliation, authority switch, backup/restore, failure resumption, rollback cutoff, and treatment of writes made after cutover.
7. Specify import-artifact lifecycle and map every object metadata field to current or proposed relational columns.
8. Keep provider-specific deployment values marked unverified until based on authorized, actual configuration; define startup, health, CORS, cookie/CSRF, connection, and persistence requirements before deployment work.
9. Preserve the security NO-GO until an authorized maintainer/reviewer documents the decision. Obtain private credential-rotation confirmation before any Supabase connection. Obtain data/research authorization before any real-data transfer.

## Dependency-ordered roadmap

1. **Security and ownership gates:** receive documented maintainer/security reviewer decision on the suspicious revision and forced update; determine the permitted scope of any later runtime work. Privately confirm deactivation/rotation of the exposed privileged credential. Confirm data custodian and research/institution approvals. Until then, no runtime, provider connection, migration, or deployment.
2. **Close design gaps:** revise the PostgreSQL, rollback, storage, and Render designs against the findings above. Resolve SQL/transaction/exception behavior, schema mappings, object-operation state machines, RLS identity, cutover authority, and recovery decisions. Keep assumptions visibly labeled.
3. **Implementation authorization and isolated development design:** obtain explicit approval for implementation after design review. Specify isolated development resources, least-privilege roles, synthetic-only data, secret handling, and rollback artifacts before writing migration code.
4. **PostgreSQL and application adapter implementation:** implement provider-specific migrations and the database adapter/query rewrite. Preserve current authentication/password verification, session-cookie properties, and membership checks; handle driver exceptions through the approved domain boundary.
5. **Private object-storage implementation:** implement the approved authorization, durable operation state, retries, reconciliation, retention, and import-artifact policy without exposing public objects or browser-held privileged keys.
6. **Authorized verification:** only after written security/runtime authorization, verify migrations, transaction/error behavior, auth/session and cross-institution isolation, upload/download/delete failure recovery, reconciliation, and database/object restore in isolated development with synthetic or explicitly authorized data.
7. **Deployment preparation and cutover:** choose actual provider-specific commands/configuration, secrets, domains/CORS, health checks, persistence, pool settings, monitoring, and restore plans. Obtain required sign-offs, execute an approved freeze/export/reconcile/cutover, and retain the rollback boundary and source snapshot.
8. **Research remains separately gated:** no A0–A4 experiments or institutional readiness scoring until their independent protocol, data, and researcher approvals are documented.

## Decision

**Implementation: NO-GO.** The four documents are a useful static planning baseline, not sufficient implementation specifications or evidence of PostgreSQL compatibility, secure object storage, provider configuration, or deployment readiness. The specific design corrections and external security/credential prerequisites above remain open. This decision does not authorize runtime testing, provider access, migration, or deployment.

No runtime operations or tests were performed.
